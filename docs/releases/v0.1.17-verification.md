## Installed upgrade checks

1. A fresh isolated 0.1.16 installation reported its version and a healthy API.
2. The 0.1.17 updater upgraded that installation to 0.1.17 and restarted it.
   Another macOS installation kept the same health instanceId, confirming that
   the updater left its LaunchAgent alone. The helper began in the package
   directory and survived npm replacing it by changing to its backup directory.
3. An isolated 0.1.15 server discovered 0.1.17 using the ordinary app-update API,
   with `updateAvailable=true` and `automaticUpdateSupported=true`. Posting to
   the same install API used by the update dialog downloaded the public package,
   installed it and restarted the server; health then reported 0.1.17.
4. Settings, prompt presets, a session file and a project file retained their
   exact SHA-256 hashes. No real customer credentials were used.

The legacy updater in 0.1.15 unconditionally attempts the user's macOS
LaunchAgent. Its isolated test used a test-only launchctl shim so it could not
stop the real installation. The new updater was tested with the real launchctl
command and an unrelated running LaunchAgent. These checks do not simulate a
real customer's model requests, Windows execution or native double-click
installation. macOS launchers remain unsigned and unnotarized.

v0.1.16 was published first. Upgrade acceptance then exposed the existing
multi-installation LaunchAgent and deleted-cwd rollback defects; the fixes were
released as 0.1.17 rather than overwriting 0.1.16's immutable artifact.
